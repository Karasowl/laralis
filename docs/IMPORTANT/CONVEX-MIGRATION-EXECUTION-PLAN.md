# Convex Migration — Execution Plan (verified audit 2026-06-04)

> Generated by a 15-agent parallel audit of all 143 API routes. Supersedes the batch ordering in CONVEX-MIGRATION-RESEARCH.md section 11.

## Key architectural facts

- **Writes already mirror automatically.** lib/supabaseAdmin.ts exports supabaseAdmin = createMirroredSupabaseClient(supabaseAdminRaw). 140 routes import this wrapped singleton, so every insert/update/delete/upsert already dual-writes to Convex when shouldWriteConvexData(table) is true. The audit trivial-write-wrap batches are therefore mostly already done — verification, not new work.
- **Reads are the real remaining work.** Each read route needs an if (shouldReturnConvexData(domain)) { read from Convex } else { Supabase } branch, behind a flag that DEFAULTS to Supabase — so adding these branches is safe and has ZERO production impact until a flag is flipped per-domain.
- Convex stores Supabase rows 1:1 by legacyId (the UUID). convex-compare reports 57/57 tables identical. Reads via listConvexDocumentsByClinic(table, clinicId) return the same row shape.

## COMPLEX items (need new Convex functions — do last)

- **DELETE /api/auth/delete-account** — Cascades through deleteClinicData over the ~14-table CLINIC_DELETE_SEQUENCE plus workspace/user tables, and finally calls Supabase Auth admin.deleteUser which is not mirrorable.
  - Needs: New Convex mutation replicating CLINIC_DELETE_SEQUENCE order and workspace/user teardown atomically; wrap the Supabase client for the mirrorable deletes and route the auth-user deletion through the convex auth bridge separately.
- **/api/workspaces/[id]/lifecycle** — Invokes deleteWorkspaceTree which performs cascading deletes across the full workspace tree; a single mirror wrap does not reproduce the multi-table cascade semantics.
  - Needs: Audit deleteWorkspaceTree for every table it touches and build an equivalent Convex cascade mutation (or ensure each underlying delete passes through the mirrored client) with matching ordering/FK semantics.
- **cleanup-draft-workspaces** — Multi-table cascade delete via deleteWorkspaceTree/deleteClinicData touching ~60 tables, plus countWorkspaceCriticalRows uses select with count:exact which has no clean generic Convex read port.
  - Needs: Convex aggregation query for clinic/workspace row counts (count:exact equivalent) and a cascade-delete mutation; wrap supabaseAdmin for the write mirror and branch the count reads.
- **recurring-expenses** — Depends on the process_recurring_expenses PL/pgSQL RPC that generates expense rows inside Postgres; that generation logic does not exist on the Convex side.
  - Needs: Port the recurrence-generation logic into a Convex mutation, OR keep the RPC on Supabase and rely on MIRRORED_RPC_REFRESH_TABLES (already maps process_recurring_expenses -> ['expenses']) to re-snapshot the affected expenses after the RPC runs.
- **send-reminders** — Joins scheduled_reminders -> treatments -> services, patients, clinics to build the reminder payload; reconstructing the nested shape from flat Convex reads is non-trivial.
  - Needs: Either a dedicated Convex query returning the reminder-with-relations shape, or sequential listConvexDocumentsByClinic calls per table reassembled in JS; writes (scheduled_reminders, email/sms_notifications) come free via the mirror wrap.
- **POST /api/public/book** — Calls the check_booking_slot_availability RPC for race-safe slot reservation; without an equivalent, concurrent public bookings could double-book.
  - Needs: New Convex query/mutation replicating check_booking_slot_availability with atomic conflict detection; then mirror the notification writes (email/sms/whatsapp all mirrored), which are otherwise straightforward.
- **POST /api/export/generate** — WorkspaceExporter reads 40+ tables across all workspace data to assemble a portable bundle; no generic helper covers workspace-scoped reads of every table.
  - Needs: A dedicated Convex exporter function enumerating all 40+ tables by workspace, OR explicitly defer workspace-level export to a post-cutover migration-tooling phase that stays on Supabase.
- **GET /api/clinic/[clinicId]/export** — Reads 40+ clinic tables with multi-table enrichment (campaign_name, source_name, service_name, patient_name, category_name) that requires cross-table name resolution.
  - Needs: A batched Convex query that fetches all clinic tables and resolves the enrichment lookups, or split into per-export-type endpoints; reuse the AI snapshot exporter pipeline where possible.
- **POST /api/export/import** — WorkspaceBundleImporter writes 40+ tables during a single import; even though it already wraps with createMirroredSupabaseClient, full-bundle import semantics need verification across every table and FK order.
  - Needs: Confirm every imported table is in MIRRORED_TABLES and that write ordering respects FK dependencies, OR build a native Convex importer; can stay on Supabase as migration tooling short-term since writes already mirror.
- **GET /api/permissions/check** — Calls the check_user_permission Postgres function; permission resolution is authorization-critical and must be exact.
  - Needs: Route reads to the already-existing api.authBridge.userHasPermission (exposed via convexUserHasPermission in lib/convex/server.ts) behind shouldReturnConvexData(); add parity tests across all roles before flipping AUTH_BACKEND.
- **GET /api/permissions/my** — Makes 3 table reads (clinics, workspace_users, clinic_users) plus the get_user_permissions RPC that returns a resolved permission map.
  - Needs: A Convex query to fetch the three membership rows plus an authBridge function that resolves the full permission map (equivalent of get_user_permissions); branch reads on shouldReturnConvexData().
- **/api/team/clinic-members** — GET calls the is_clinic_member RPC and getAuthUserProfilesByIds (Supabase Auth admin API, not mirrorable); POST is mechanical but the GET path is RPC- and auth-bound.
  - Needs: Convex equivalent of is_clinic_member (or inline the membership check) plus a path to resolve auth user profiles through the convex auth bridge; do the POST mirror wrap independently first.
- **/api/invitations/accept/[token]** — POST orchestrates correlated writes across invitations, workspace_users and clinic_users with transaction semantics, and calls getAuthUserProfileById against Supabase Auth admin.
  - Needs: A single Convex mutation that atomically creates the membership rows and marks the invitation accepted; resolve the auth profile via the convex auth bridge rather than Supabase Auth admin.
- **GET /api/reports/summary** — Joins treatments and patients then feeds analytics/calculateKPIs; Convex has no nested select so the join must be reconstructed in memory with KPI accuracy preserved.
  - Needs: Fetch treatments and patients separately via listConvexDocumentsByClinic, join in-memory by patient_id per the patients.ts reference pattern, then pass to the existing calculateKPIs helper and regression-test the numbers.
- **GET /api/prescriptions/[id]** — Requires a multi-level prescription -> treatment -> service join; generic helpers do not cover chained joins (note: services IS mirrored, contrary to the raw audit note, but the chained join still needs custom logic).
  - Needs: A dedicated Convex query that walks prescription -> treatment -> service and bundles prescription_items, or staged listConvexDocumentsByClinic reads reassembled in JS.
- **/api/tariffs** — Needs nested services -> service_supplies -> supplies lookups plus settings_time/fixed_costs/assets cost aggregation to recompute tariff costs; the tariffs table is also deprecated.
  - Needs: A Convex query returning per-service computed costs (the same nested aggregation), then branch GET/POST on shouldReturnConvexData() and wrap writes; first decide whether the deprecated tariffs table is even worth migrating.
- **POST,GET /api/reset** — Wide multi-table delete/reseed across ~14 clinic tables flagged high risk; a mistake wipes clinic data, and the GET count branch needs Convex aggregation.
  - Needs: Wrap supabaseAdmin with createMirroredSupabaseClient so deletes mirror, and add Convex count reads for the GET branch; gate behind heavy tests given destructiveness.

## Stays on Supabase / infra (do not migrate now)

- POST /api/analytics — pure analytics-event logging endpoint with no DB reads/writes; nothing to migrate.
- POST /api/ai/query — QA/diagnostic mode driven by deterministic mock data via aiService; not a production data path, stays on Supabase for now.
- POST /api/auth/convex-bridge — the convex-auth bridge itself; writes credentials directly to Convex's authBridge mutation and touches no Laralis tables, so it is the target infra, not a migration candidate.
- DELETE /api/account/delete — deprecated, returns HTTP 410 Gone; no migration needed.
- Workspace-level export/import tooling (POST /api/export/generate, POST /api/export/import) — may legitimately stay on Supabase short-term since import already mirrors writes; revisit only if full native Convex export tooling is prioritized.

## Top risks (with mitigations)

- Analytics/break-even numeric drift: ~18 reporting routes replicate Supabase SQL aggregation in JS (markup-vs-margin, depreciation, contribution margin, quartiles). Any rounding, date-bucketing, or filter mismatch silently corrupts revenue/break-even cards. Mitigation: run DATA_BACKEND=dual_read with shouldCompareConvexData to diff both backends in prod before flipping DATA_READ_BACKEND=convex per domain.
- Lost nested selects / in-memory joins: Convex has no relational nested select, so every join route (service-roi, services/top, treatments/frequency, reports/summary, channel-roi, prescriptions/[id], tariffs) must reassemble shapes by hand. Bugs here drop or duplicate rows. Mitigation: a shared, tested join helper plus per-route row-count parity assertions.
- Auth + permission cutover (AUTH_BACKEND=convex): permissions/check, permissions/my, team membership, and invitation accept depend on Postgres RPCs (check_user_permission, get_user_permissions, is_clinic_member) and Supabase Auth admin profile lookups that are not mirrorable. A resolution mismatch causes either lockouts or privilege escalation. Mitigation: exhaustive role-matrix parity tests against the existing convexUserHasPermission before flipping, and keep auth flip independent from data flip.
- Destructive cascade fidelity: delete-account, workspace lifecycle, cleanup-draft-workspaces, and reset cascade across 14-60 tables in FK order. If the Convex equivalent misses a table or order, you get orphans or partial deletes with no transaction rollback. Mitigation: build dedicated Convex cascade mutations mirroring CLINIC_DELETE_SEQUENCE exactly, test on disposable workspaces, and gate behind dual_write verification.
- Write-mirror completeness and silent failures: full read parity is only safe if dual-write has been live long enough that Convex holds every row. Unwrapped writers (still ~40 routes pre-batch-1) or a mirror error swallowed at runtime leaves Convex stale, so reads return wrong/empty data after cutover. Mitigation: land all write wraps first (batches 1-2), add a per-table Supabase-vs-Convex row-count reconciliation job, and alert on mirror failures before enabling any convex read.

## FINAL STATE (2026-06-05) — user-facing read+write parity COMPLETE

### Writes: no gap remaining
`createClient()` in `lib/supabase/server.ts` **already** returns a Convex-mirrored
client (`createMirroredSupabaseClient`), exactly like `supabaseAdmin`. So EVERY write
path — service-role (`supabaseAdmin`) and SSR (`createClient`) — dual-writes to Convex
when `shouldWriteConvexData(table)` is on. Batch 1/2 "write wrap" items are therefore
already satisfied by the two client factories; no per-route wrapping is needed.
(`saveMfaPreferences` also wraps defensively — idempotent via `MIRRORED_CLIENT_MARKER`.)

### Reads: 96 / 110 GET routes carry a flag-gated Convex branch
All **user-facing** GET reads are migrated, including the previously-deferred complex
group: permissions/check, permissions/my, team/{clinic-members,workspace-members,custom-roles},
reports/summary, prescriptions/[id], tariffs, ai/chat/history, bookings, public/*, and the
follow-ups **invitations**, **invitations/accept/[token]**, **settings/security/mfa**,
**medications**, **settings/{user,preferences,notifications,booking}**.

The **operational cron jobs** and **snapshot metadata** reads are also migrated now
(flag-gated, default Supabase; writes/processing untouched): cron/complete-appointments,
cron/snapshots, cron/cleanup-draft-workspaces, cron/send-reminders (4-level join
FK-reassembled in JS), cron/retry-notifications (+ lib/notifications/retry-queue), and
snapshots + snapshots/[snapshotId] (clinic_snapshots metadata; the files stay in
Supabase Storage). Only **8** GET routes remain on Supabase — all structurally
non-migratable (see below).

Key correctness work landed this phase:
- **authBridge.userHasPermission** rewritten to replicate `check_user_permission`
  (migration 76) EXACTLY — super_admin carve-outs, allowed_clinics, encoded-JSONB
  custom_permissions denies, custom_role_templates+base_role, clinic-beats-workspace
  precedence, `is_active = true` strict. Deployed to Convex (typecheck clean).
- **Encoded JSONB key decode**: added `decodeConvexFieldName`/`decodeConvexValue`
  (exact inverse of `encodeConvexValue`) in `lib/convex/legacy.ts`; applied wherever a
  semantic-keyed JSONB map is read back (permissions/my, team/*, invitations, user_settings,
  mfa). Without it, `custom_permissions`/`permissions` overrides silently never applied.
- **Permission-subsystem flag unified** on `role_permissions` + `getAuthBackend()==='convex'`
  so enforcement guard and all self-service/team routes flip atomically.

### The 8 GET routes WITHOUT a Convex branch — structurally non-migratable
| Route(s) | Category | Reason |
|---|---|---|
| migration/convex-compare, convex-full-sync, convex-health, convex-sync | Migration tooling | Read/compare BOTH backends BY DESIGN — must never read only Convex |
| clinic/[clinicId]/export | Backup/DR | Dumps Supabase via `information_schema` table discovery (export edge) |
| snapshots/discover | Backup/DR | **Impossible on Convex** — introspects Supabase `information_schema` (no catalog in Convex) |
| reset | Destructive admin | Wipes ~14 Supabase tables; GET count branch is admin tooling (audit: do-not-migrate) |
| cron/recurring-expenses | Operational | **Pure Postgres RPC** (`process_recurring_expenses`) — no read to migrate; the mirror refreshes the expenses snapshot after the RPC |

Caveat for the migrated cron jobs: they honor the same per-domain read flag as the UI, so a
cron only reads Convex once its domain's `DATA_READ_BACKEND_<DOMAIN>` is flipped. Flip a
cron's read domain to Convex only after that domain's data is verified in sync (otherwise a
cron could process stale/duplicate rows); ideally flip cron read domains together with
`DATA_WRITE_MODE` at full cutover.

### Operator next steps (canary)
1. Per domain, set `DATA_READ_BACKEND_<DOMAIN>=convex`; observe `convex-compare`
   (or `DATA_COMPARE_CONVEX=1` with `dual_read`) to diff both backends in prod.
2. Permission subsystem flips together via a single `DATA_READ_BACKEND_ROLE_PERMISSIONS=convex`.
3. Auth cutover (`AUTH_BACKEND=convex`) switches permission resolution to the bridge too.
4. Only after read parity is verified per domain, flip `DATA_WRITE_MODE_<DOMAIN>=convex`
   (convex-only writes), then revisit cron/backup migration.
